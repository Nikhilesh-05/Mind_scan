# MindScan - Complete Technical Review & Project Breakdown

## 1. High-Level Architecture
MindScan is a modern, decoupled web application. It follows a classic **Client-Server Architecture**:
- **Frontend (Client):** A Single Page Application (SPA) responsible for the UI, state management, media capture (microphone/webcam), and client-side ML processing (face-api.js).
- **Backend (Server):** A RESTful API server that handles business logic, database transactions, user authentication, NLP processing for chat/audio summaries, and third-party API orchestration (Sarvam AI).
- **Database:** A relational database used for persistent storage of user profiles, session metadata, chat logs, audio features, and video summaries.

---

## 2. Technology Stack & Why It Was Chosen

### A. Frontend
- **React 18:** Component-based UI library. Allows for dynamic, reactive interfaces without reloading the page.
- **Vite:** Build tool and development server. Replaces Webpack. Extremely fast Hot Module Replacement (HMR) and optimized build speeds.
- **Tailwind CSS:** Utility-first CSS framework used for rapid UI development and styling the "glassmorphism" dark theme.
- **Framer Motion:** Animation library used for smooth page transitions, interactive hover states, and dynamic charts.
- **Zustand:** Lightweight global state management library used to track the user's current session progress (Chat -> Audio -> Video modules).
- **Axios:** HTTP client for making API requests to the FastAPI backend, with interceptors built-in for handling JWT token injection.
- **face-api.js:** A JavaScript facial recognition library running entirely in the browser (client-side) to detect emotions without sending heavy video frames over the network.

### B. Backend
- **FastAPI (Python):** A modern, high-performance web framework for building APIs. Chosen for its automatic Swagger documentation, async support, and type validation (Pydantic).
- **SQLAlchemy 2.0 (Async):** Object-Relational Mapper (ORM) mapped to an asynchronous Postgres/SQLite driver. Allows Python objects to represent database tables and perform non-blocking queries.
- **Alembic:** Database migration tool for SQLAlchemy. Used to track changes to the database schema over time.
- **Pydantic:** Data validation library. Used as the core of FastAPI's request/response models to ensure data strictness.
- **PyJWT & Passlib (bcrypt):** Libraries used to hash user passwords securely and generate JSON Web Tokens (JWT) for secure, stateless authentication.
- **httpx:** An asynchronous HTTP client (like Requests, but async) used to securely bridge our backend to the external Sarvam AI API without blocking the server.
- **fpdf2:** A lightweight Python library for generating dynamic PDF documents (the final downloadable report).

### C. Database Layer
- **PostgreSQL / SQLite:** Relational database used to structure data into linked tables (Users, Sessions, ChatResults, AudioResults, VideoResults, AnalysisReports).

## 3. Core Modules & Technical Logic Flow

### Module 1: Authentication & Authorization Flow
1. **Registration:** User enters email/name/password. Backend receives it, uses `bcrypt` to hash the password securely, and saves the User record to the DB.
2. **Login:** User provides credentials. Backend verifies the password hash. If successful, it constructs a **JWT (JSON Web Token)** containing the `user_id` and an expiration time, signs it with a secret key, and sends it back.
3. **Session State:** Frontend stores the JWT in `localStorage`. Every subsequent request to the backend includes this token in the `Authorization: Bearer <token>` header. A FastAPI dependency (`get_current_user`) decodes this token on every protected route to identify the user.

### Module 2: Chat Analysis (Text Modality)
- **Frontend Logic:** A React chat UI that pushes strings to the backend logic.
- **Backend Logic (`/chat/message`):** 
  - Uses an NLP/Pattern Matching engine to score sentiment (positive/negative percentages). 
  - Scans user text for PHQ-9 (Patient Health Questionnaire) keywords like "tired", "sleep", "hopeless" to extract specific clinical signals.
- **Database:** Every message and its calculated sentiment/PHQ-9 indicators are saved in the `ChatResult` table, mapped via Foreign Key to the current `Session`.

### Module 3: Voice Analysis (Audio Modality)
- **Frontend Logic (`navigator.mediaDevices.getUserMedia`):** Uses the browser's MediaRecorder API to capture the user's microphone. Audio data is painted onto an HTML5 Canvas using the Web Audio API (`AnalyserNode`) to create a real-time waveform.
- **Backend Logic (`/audio/analyze`):** The audio blob is sent as a `multipart/form-data` file. The backend (currently mocked for Whispher) mathematically simulates pitch extraction (Hz), speaking rate (WPM), and pauses to determine prosodic emotional features (e.g., flat affect vs. expressive).
- **Database:** Extracts are saved to the `AudioResult` table.

### Module 4: Facial Expression (Video Modality)
- **Frontend Logic (Client-Side ML):** 
  - Rather than streaming large video files to the backend, we run AI in the browser to save bandwidth and server compute. 
  - We load the `@vladmandic/face-api` TinyFaceDetector neural network weights.
  - Every 500ms, the canvas captures a snapshot of the webcam. `face-api.js` analyzes the geometry of the face to output an emotion map (happy, sad, neutral, angry, etc.).
  - **Technical Smoothing:** Because neural networks flicker rapidly, we implemented a **Majority-Vote Smoothing Algorithm**. It stores the last 3 detections in an array and only updates the UI if the majority vote reaches a threshold. Furthermore, custom mathematical multipliers (e.g., multiplying `sad` score by x25) were engineered into the frontend to counteract the baseline model's extreme bias toward predicting "neutral".
- **Backend Logic (`/video/frame`):** The frontend sends a lightweight JSON payload of the aggregated emotions (not the video) to the server to be saved in the `VideoResult` table.

### Module 5: Sarvam AI Multimodal Fusion & Report Generation
- **The Orchestration Route (`/report/generate`):**
  1. **Data Aggregation:** The backend queries the database for the user's active session, retrieving the `ChatResult`, `AudioResult`, and `VideoResult` rows.
  2. **Prompt Engineering:** A large prompt string is constructed that concatenates all text sentiment scores, audio prosodic flags, and video emotion distributions.
  3. **External API Call (`httpx`):** The backend makes an asynchronous POST request to the Sarvam AI `v1/chat/completions` REST endpoint using the `sarvam-m` model. 
  4. **JSON Enforcement:** The prompt strictly demands a JSON output. If Sarvam responds with JSON, the backend parses it. If it fails, a deterministic local math fallback generates the score.
  5. **Storage:** The final fused risk string is saved to the `AnalysisReport` table.
- **PDF Generation (`/report/download/{id}`):**
  - **Backend:** Uses the `fpdf2` library. We implemented custom Unicode sanitization (`_safe()` function) to strip emojis/complex characters that break standard PDF encoding, and engineered dynamic `new_x`/`new_y` margin wrapping logic.
  - **Frontend:** To bypass Axios interceptor corruption on binary data, a raw `XMLHttpRequest` is spawned with `responseType: 'blob'`, forcing the browser to securely download and construct the `application/pdf` binary file on the client system.

## 4. Most Likely Questions They Will Ask You:

**Q: How does the app scale if multiple users use the Video analysis at the same time?**
**A:** Very well. Because we use `@vladmandic/face-api` directly in the React frontend, all the heavy neural network video processing is offloaded to the user's local CPU/GPU inside the browser. Our backend server is untouched by video streams and only receives a lightweight JSON packet containing the final emotion numbers.

**Q: How are you securing user tokens?**
**A:** We use JWT (JSON Web Tokens). It allows stateless authentication. The backend doesn't need to look up a session table for every request; instead, the token mathematically proves the user's identity via a secret signing key (`HS256` algorithm). Passwords are never stored in plaintext—only their bcrypt hashes.

**Q: Why use FastAPI over Flask or Django?**
**A:** FastAPI is asynchronous by default, meaning when we make long external HTTP calls (like to the Sarvam AI API), the server doesn't block other users from making requests. It also has automatic data validation via Pydantic — if the frontend sends a string when an integer is expected, FastAPI rejects it instantly before it touches our business logic.

**Q: What happens if Sarvam AI's API goes down? Does the app crash?**
**A:** No. We engineered the backend `/report/generate` endpoint with a try-except fallback block. If the `httpx` async call to Sarvam AI times out or returns a non-200 status code, the application catches the exception and falls back to a deterministic, locally calculated risk score based on the raw metrics already saved in the database.
